> Status: **черновик для АРХКОМ** — подготовка к решению, НЕ реализация.
> Автор: `@GCW: Product Architect`, 2026-09-28. База: бриф владельца (пп. 7–8, дословно
> по интенту), 01-CHARTER.md §2.7/§8, 07-INTEGRATION.md И6* (RCE-класс: «отдельный
> АРХКОМ+ADR+threat model»), моки `design/stand/desktop.html` и `explorer.html`,

## 1. Проблема и ценность

Дословно по брифу: «Раздел с Рабочим столом и терминалом (в котором реально можно
работать с файлами)» и «функциональный интерфейс работы с Агентами и проводник
файлов проектов (чтобы можно было их удалённо подключать… подключать как удаленный
репозиторий и работать с ним, в том числе — редактировать файлы)».

Что владелец получит:

1. **Терминал на подключённом хосте из браузера и телефона** — без прыжков по
   ssh-сессиям и без «носка» ноутбука.
2. **Проводник проектов**: дерево и файлы удалённых проектов как подключённых
   репозиториев; чтение, затем правка с диф-ревью и git-операции.
3. **Агент рядом**: мок уже рисует точки «agb правит сейчас», подсветку правимых
   строк и кнопку «Открыть диф» — видно, кто и что меняет в файле, пока ты его
   смотришь; дополнится lock-индикацией и сведением с сессиями Коры.

Связка с ADR 0019 (NO-DRIFT): в память пишет только харнесс; Кора — view+relay над
сессиями. Проводник — той же природы: view+relay над файловой системой хоста. Наш
редактор **не пишет в память** и не форкает сессии; правка файла — обычная правка на
диске хоста, которую харнесы и git видят как локальную. Дрифт невозможен по
построению, потому что мы не касаемся стора. Терминал и файлы — новые исполнительные
поверхности RCE-класса: по И6* стартуют только после собственного АРХКОМ, ADR и
threat model; эта бумага — вход в тот гейт.

## 2. Варианты архитектуры

Общие требования: outbound-транспорт от хоста (наследие vesmaro-agent: «no listening
ports»), identity уже есть (mne_-enrollment), аудит и redaction — на борде, белый
список корней проектов — на хосте.

### A. Расширить vesmaro-agent (рекомендуется)

Новая outbound-нога «workbench» (протокол v0.2, аддитивно; VERSION-handshake §5 и
раздел совместимости §7 для этого и существуют; AGW-18 уже добавил постоянную ногу
поверх poll-модели — прецедент). Борд мультиплексирует терминальные и файловые
сессии владельца в этот поток; агент поднимает PTY и файловый API в пределах белого
списка корней.

- Безопасность: одна цепочка доверия (enrollment + per-child capability-токены
  AGW-19), один канал, один путь обновлений. Нога включается флагом в конфиге
  агента, по умолчанию выключена.
- Сложность: средняя. Нужна новая concurrency-модель в агенте (сегодня — poll-цикл,
  потребуется постоянный стрим) и протокольная работа v0.2.
- Соответствие архитектуре: высокое — outbound-only сохранён; «сеть не проблема
  агента» не нарушается.
- Риск R1 (честно): сегодня «the board never gains an inbound execution channel» —
  терминал это execution-канал, пусть и поверх outbound-сессии агента. Это
  **сознательный сдвиг ратифицированного инварианта** vesmaro-agent: требует явной
  ратификации владельцем, а не тихого расширения протокола.

### B. Отдельный lightweight daemon с узким файловым API

Второй бинарник на хосте: только PTY + файловый API, никакого пересечения с задачами.

- Безопасность: изолированная поверхность; компрометация не открывает задачный
  контур.
- Сложность: вторые enrollment, presence, обновления, мониторинг — операционный
  дубль для single-tenant LAN+VPN с 3–4 хостами.
- Соответствие: низкое. Ломает философию «one binary» vesmaro-agent и создаёт
  **второй trust anchor** для той же способности (RCE на хосте) рядом с уже
  enrolled-агентом. Два якоря доверия хуже одного. Отклоняется.

### C. SSH-мост с борда (серверный host-executor — формулировка из И6)

Борд подключается к хостам по SSH (PTY + sftp); на хостах ничего нового не ставится.

- Безопасность: проверенная десятилетиями модель, разграничение через системных
  пользователей. Но борд получает **на хранение SSH-ключи ко всем хостам** — секрет
  нового класса; компрометация борда = компрометация всех хостов (в варианте A
  ключей нет — есть живая outbound-сессия, которую можно отозвать). Bootstrap ключей
  (authorized_keys) — ручная работа владельца на каждый хост.
- Сложность: минимальный путь к первому релизу, но серверная SSH-нога потом не
  переиспользуется при переходе на A — двойная работа.
- Соответствие: «сеть не проблема агента» ломается в другую сторону — хост обязан
  принимать входящие соединения из сети борда. Для VPN приемлемо, но это второй
  транспорт рядом с существующим outbound-агентом.
- Вердикт: держать как **fallback**, если нога v0.2 забуксует; обе ноги сразу не
  строить.

**Рекомендация: A.** Один trust anchor, outbound-only сохранён, identity, протокол
и механизм совместимости уже спроектированы под эволюцию; терминал и файлы получают
один канал аудита и один путь обновлений. C — план Б на случай провала v0.2-ноги;
B — нет.

## 3. Threat model (STRIDE-набросок)

Актив: RCE на хосте (терминал), чтение/запись произвольных файлов. Злоумышленники:
украденный ui-токен (главный), MITM в LAN/VPN, скомпрометированный борд, баг
path traversal в файловом API.

| STRIDE | Угроза | Контролы |
| --- | --- | --- |
| S | подмена владельца / борда / агента | сплит ui/machine-токенов (ADR 0009), mne_-identity агента, TLS; терминальная сессия живёт только внутри owner-session |
| T | инъекция команд в поток | нумерация сообщений и session-id: агент исполняет только команды активной сессии; ресинк — явная процедура |
| R | «кто выполнил команду» | аудит каждой команды на борде (append-only: кто / хост / команда / код возврата / время) + локальный хвост-журнал на агенте как дублирующий |
| I | секреты в выводе терминала и в файлах; traversal за корни | единый redaction choke-point (ADR 0019) на всём, что течёт в браузер; белый список корней проектов в конфиге агента, fail-closed, резолв symlink и «..»; маскирование в UI |
| D | зависший PTY, флуд | лимит сессий на хост, таймаут неактивности, kill-switch сессии в UI, отдельный релей-процесс (прецедент vesmaro-session-relay) |
| E | кража ui-токена → RCE | step-up PIN (модель ADR 0019, TTL ~15 мин) на открытие терминала и на запись; нога выключена по умолчанию и включается владельцем **на хосте**; yolo off, confirm по умолчанию |

Честное ограничение: белый список корней ограничивает файловый API, но **не
терминал** — из shell можно уйти в любой путь. Поэтому главные контролы терминала —
step-up + opt-in на хосте + аудит, а не scope.

Минимальный набор для «можно выпускать» (релиз-гейт каждой фазы): (1) opt-in нога
на хосте, по умолчанию выкл; (2) step-up PIN на терминал и запись; (3) аудит каждой
команды и файловой записи; (4) redaction choke-point на исходящем в браузер потоке;
(5) белый список корней для файлового API; (6) kill-switch + лимит сессий;
(7) confirm-режим по умолчанию, yolo — per-session opt-in с аудитом.

## 4. UX-каркас

Моки уже рисуют каркас (`design/stand/desktop.html`, `explorer.html`):

- **Рабочий стол**: окна «Терминал»/«Файлы» + док, Ctrl+`, Esc очищает ввод, не
  закрывая окно; бейдж «эксперимент» в сайдбаре; анонимный визит — гейт (07k).
- **Проводник**: дерево (ветка main) + редактор с табами + панель «Агент рядом»;
  точки «agb правит сейчас» и подсветка правимых строк; кнопка «Открыть диф»;
  модал «Подключить репозиторий» (URL git@/https, ветка, токен только по ссылке
  env:/file: — сам секрет ввести нельзя, маскирование, «Проверить»).

Добавится в продукте: выбор хоста (в моке промпт фиктивен); оверлей step-up PIN;
confirm-модалка опасных команд (эвристика классов `rm -rf`/`sudo`/`push --force`;
ложные срабатывания приемлемы — это confirm, не блок); диф-ревью перед сохранением
файла; индикация «кто в сессии» (владелец / агент / оба — расширение существующих
точек); честный статус ноги в topbar (live-пилюля уже есть); kill-кнопка сессии.

## 5. Фазирование

Каждая фаза самостоятельна по ценности и несёт свой надбавочный гейт поверх базового
набора §3.

| Фаза | Что | Ценность | Гейт сверх базового |
| --- | --- | --- | --- |
| T1 | Read-only проводник через агента: дерево, чтение файлов, статус git (ветка / dirty) | «видеть проекты из телефона» | read-only нога протокола; traversal-тесты; redaction |
| T2 | Терминал: PTY-сессия на хосте, confirm-режим | «работать с хостом из браузера» | step-up PIN; opt-in на хосте; аудит команд; kill-switch; лимиты сессий |
| T3 | Редактирование с диф-ревью: запись только через диф-модалку, конфликт-детект (mtime/ETag), lock «агент правит сейчас» | «поправить файл, не открывая ноут» | аудит записей; конфликт-семантика; лимит размера файла |
| T4 | Git-операции: status/diff/log, коммит, push по явному remote (креды хоста; токены env:/file:) | «удалённый репозиторий» из брифа | push после step-up; force-push только в yolo |

Порядок T1→T2→T3→T4; T1 и T2 **не объединять** в один срез — разные классы риска и
разные гейты. Клонирование по URL из модала «Подключить репозиторий» — внутри T4; до
того проводник работает только с уже существующими clone на хостах.

## 6. Открытые вопросы владельцу

1. **Объём первого релиза.** Рекомендация: T1 первым срезом, T2 вторым; T3/T4 —
   после обкатки T1+T2.
2. **Хосты пилота.** Рекомендация: 1–2 хоста (прецедент soak-теста агента на
   vpn.us), начать с хоста, где живёт vesma-eyes.
3. **Git-провайдер и креды.** Рекомендация: GitHub (репозитории уже там); push —
   кредами хоста, борд токены не хранит, только ссылки env:/file: как в моке.
4. **Хранение аудита.** Рекомендация: append-only SQLite на борде, retention
   90 дней, локальный хвост-журнал на агенте. Открыто: срок жизни и нужен ли экспорт.
5. **Оффлайн-режим.** Рекомендация: не делать — нога живёт только при живом
   outbound-соединении; оффлайн = честный статус «нет сессии», без кэша.

## 7. Рекомендация по АРХКОМ

**Полный АРХКОМ, не дизайн-пас.** Причины: (1) RCE-класс — по действующим правилам
доверенные поверхности (исполнение, доступ к данным) проходят расширенное ревью до
старта работ; (2) рекомендованный вариант A сдвигает ратифицированный инвариант
vesmaro-agent «борд никогда не получает execution channel» — это изменение
архитектурного контракта замороженного протокола, а не UI-деталь; (3) прецедент
ADR 0019: руление сессиями (тоже исполнительная поверхность) прошло полный комитет с
системщиком и безопасником — и это окупилось.

Состав: Product Architect (эта бумага — вход), Senior System Engineer (протокол
v0.2, PTY, стрим-нога), Senior Security Engineer (полный threat model из наброска
§3), Tech Lead (председатель, ведение ADR). Выход комитета: ADR (номер в ряду
0022+) + ратифицированный threat model + зелёный свет T1.
