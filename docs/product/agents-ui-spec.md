## 0. Цель одним абзацем

Владелец, открыв карточку задачи, видит картину работы агента целиком: какие
отчёты приходили (уже работает), каких специалистов-детей агент подключал,
сколько они работали — и может провалиться в сессию специалиста, чтобы
понять, как шла работа. Рядом, в ростере «Агенты» (ME-014), карточка хоста
сообщает, чем этот харнес загружен: специалисты, скиллы, плагины,
инструкции. Никакого содержимого сессий и файлов харнесов в борд не
уезжает — только имена, счётчики, пути-факты.

Формула спеки: **агент — источник фактов, борд — хранение и UI, контент
остаётся на хосте всегда**.

## 1. ME-020 — вердикт MVP по четырём требованиям владельца

Дословные требования (владелец, 2026-09-28) и вердикт по каждому: MVP или
фаза 2. Прицел MVP — «владелец видит картину работы агента в карточке
задачи».

| # | Требование владельца | Вердикт | Что входит |
| --- | --- | --- | --- |
| 1 | Промежуточные и финальные отчёты в карточке задачи | **Закрыто — уже работает** | Таб «Отчёты» (`/tasks/:id?tab=reports`): хронологические карточки intermediate/final, superseded-флаги, «Вернуть в работу» (UI-8). Работы ноль — фиксируем как закрытое. |
| 2 | Видеть, каких специалистов подключал агент (харнес) | **MVP** | Блок «Специалисты и сессии» в табе «Исполнение»: по каждому ребёнку — имя специалиста, харнес, счётчик тул-каллов, длительность, статус. Источник — session-факты агента (§2). Сегодняшний блок «Кто работал» (UI-31) атрибутирует исполнителей-хостов; блок добавляет уровень детей-специалистов. |
| 3 | Проваливаться в отдельные сессии специалистов | **MVP, с честной границей** | Строка сессии → deep-link в существующий read-only просмотрщик Коры (`/kora/sessions/{executor_id}:{native_id}`, slice 2: редакция-choke-point, аудит `session.transcript_viewed`). Новый контент-путь в MVP НЕ строится: сессии хостов, чей стор борд не читает, честно отвечают 404-плашкой покрытия (см. §5). |
| 4 | Визуальное дерево «какие субагенты где, на какие подзадачи» («как в самом zcode») | **Фаза 2** | Дерево требует структуры подзадач (parentId-цепочки сессий и/или разбор toolCall к агент-тулам). MVP даёт плоский список по задаче (сгруппированный по assignments); формат факта уже несёт `parent_native_id` (§2.1), чтобы фазе 2 не менять контракт. |

Развязка MVP/фаза-2 уже согласована с уставом агента: charter v2 M2 требует
«каждый child агента имеет session-факт в карточке ≤ 60 с после выхода
ребёнка; транскрипт просматривается read-only» — это и есть границы MVP.
Дерево (№4) уставом не обещано — фаза 2.

## 2. Формат session-факта и шов assignment → child → session-dir

### 2.1 Вердикт по формату: additive `sessions[]` на discovery-ноге

**Принят вариант устава (charter v2 §2.5):** агент постит session-факт
дополнительным полем `sessions[]` в `POST /api/executors/{id}/discovery`,
событийно — на выходе ребёнка (child exit), часовой sweep — догоняющий.
Альтернатива «session-факт как intermediate-отчёт» **отвергнута**
окончательно: машинные строки не принадлежат ленте чтения владельца —
лента отчётов остаётся человеческой.

```json
{"harnesses": [ /* §3, без изменений */ ],
 "sessions": [{
   "task_id": "ME-048",
   "harness": "pi",
   "native_id": "sess_a1b2c3",
   "specialist": "gcw-tech-lead",
   "path": "/home/u/.local/share/vesmaro/pi-sessions/sess_a1b2c3.jsonl",
   "tool_calls": 12,
   "duration_s": 340,
   "started_at": "2026-09-30T10:04:11Z",
   "ended_at": "2026-09-30T10:09:51Z",
   "parent_native_id": ""
 }]}
```

Поля:

- `task_id` — обязательный; связь с задачей борда из spawn-реестра агента
  (assignment→child, §2.4 устава). Без `task_id` факт отбрасывается бордом
  (dropped + аудит, паттерн discovery-имён).
- `harness` — словарь `zcode|vscode|pi`; значение вне словаря — dropped +
  аудит (грамматика discovery без изменений).
- `native_id` — id сессии в нативном сторе харнеса, уникальный в рамках
  исполнителя. Ключ склейки с Корой: id сессии Коры = `"{executor_id}:{native_id}"`
  — deep-link из карточки работает без трансляций.
- `specialist` — назначение ребёнка, которое агент породил (subagent_type
  спавна); best-effort, может быть пустой строкой. Имя — публичный факт,
  не содержимое.
- `path` — локальный путь хоста; **рендерится только в карточке задачи**
  (ui-класс), никогда на публичных поверхностях (устав §2.5).
- `tool_calls`, `duration_s` — счётчик из ограниченного чтения файла и
  часы супервизии. Числа, не содержимое.
- `parent_native_id` — additive, omitempty; топливо дерева фазы 2
  (parentId-цепочки pi-формата фиксируются уже сейчас, разбор — потом).

Семантика (устав D5 дословно): факт **агент-авторизован** — id и счётчики
выводимы из spawn-реестра, часов супервизии и ограниченного чтения файла
сессии; ничто в отчёте или выводе ребёнка не может создать или изменить
session-факт. Дедуп по id, ≤ 32 строк на пост, пост только на событиях
жизненного цикла агента. Контент сессии не покидает хост ни в каком
варианте (never-list 5).

### 2.2 SE-оценка шва (без кода)

| Поверхность | Оценка | Вывод |
| --- | --- | --- |
| Класс доверия | `sessions[]` едет тем же executor-токеном, той же identity-match ногой (URL id = токен → 403 при несовпадении), тем же бюджетом 60/60 с, что heartbeat/discovery | Новый класс доверия НЕ вводится; пост-факт расширяет существующую ногу. |
| Подделка ребёнком | У ребёнка нет токена исполнителя; loopback-токены ребенка — per-child capability для записи отчётов, не для discovery-ноги; «нет child-триггеримого пути постинга» — инвариант устава | Ребёнок не может ни постить, ни изменить session-факт. Держать инвариант в ревью агент-лейна. |
| Спуфинг/загрязнение | Багги/вредоносный агент может лгать только о фактах СВОЕГО исполнителя — тот же уровень доверия, что discovery сегодня (advisory mirror, never authority) | Приемлемо; стор — зеркало, не авторитет. Дедуп + ≤32 + словарь harness ограничивают объём. |
| Валидация task-linkage | Дёшево и достаточно: у задачи должен существовать assignment, claim-нутый этим исполнителем (`claimed_by_executor` — авторитетная атрибуция борда); иначе drop + `discovery.rejected`-паттерн аудита | Обязательная борд-проверка; отсекает чужие/несуществующие задачи без новой модели доверия. |
| Раскрытие путей | `path` — потенциально чувствительный факт файловой системы хоста | Только ui-класс, только карточка задачи; не в OPEN-чтении реестра, не в SSE-словаре, не в mnd_-классе (пока владелец не решит иное, §7). |
| Секреты в счётчиках/именах | Имена специалистов/скиллов — публичные факты (дисциплина PROTOCOL §3); счётчики — числа; чтение файла сессии ограничено по размеру (как парс pi-settings) | Контент-утечек нет by construction; ограничение чтения — обязательный пункт агент-лейна. |
| Rate/бёрст | Выход K детей подряд → K постов ≤ 32 строк; бюджет 60/60 с на клиента; 429 → агент дошлёт на следующем тике (sweep-догоняющий) | Достаточно; отдельного лимитера не вводить. |
| Просмотр транскрипта | НОВОГО контент-пути в MVP нет: deep-link переиспользует замороженный slice-2 маршрут (ui-класс, ре-валидация реестра на каждый ответ, единый choke-point редакции, seq-курсор, аудит) | Граница контента не расширяется. Это ключевое SE-условие MVP-вердикта требования №3. |

### 2.3 Источник сессий: `sessions[]` агента vs kora-scan — вердикт и миграция (ME-056)

Проблема сверки ME-040: стор Коры наполняет поллер-семейный kora-scan
(`POST /api/executors/{id}/kora-scan`, полные листинги с `drop_missing`),
а устав D5 ведёт `sessions[]` агента через discovery. Хост на Go-агенте
без kora-сканера сегодня не покажет сессии в ленте Коры.

**Вердикт: две ноги с разными ролями и одним ядром сканирования, не выбор
одной.**

- **`sessions[]` (агент, discovery-нога) — источник карточки задачи.**
  Только агент знает связь задача→ребёнок (spawn-реестр); kora-scan не
  имеет task-linkage и получить его не может. Событийная семантика
  (child exit ≤ 60 с) соответствует M2 устава.
- **kora-scan push — источник ленты Коры.** Лента — хост-широкий листинг
  всех сессий стора (включая не-агентские), с состояний live/idle/dead и
  drop_missing-семантикой «стор — авторитет». Это другой продукт, другой
  контракт (ADR 0019, заморожен), другой стор.

**Миграция (разворачивает ME-056):** Go-агент берёт на себя ОБЕ ноги на
одном read-only ядре чтения сиджей (zcode `.zcode/cli/sess_*`, pi
`~/.local/share/vesmaro/pi-sessions/*.jsonl`): (а) событийные
`sessions[]` для карточки; (б) периодический push в СУЩЕСТВУЮЩИЙ маршрут
`kora-scan` — контракт заморожен, executor-токен уже принимает
(`Auth: the executor's OWN token`, server/app.py), борд менять не нужно.
Единая дисциплина `native_id` между ногами обеспечивает склейку: id Коры
`{executor_id}:{native_id}` совпадает с фактом карточки — deep-link и
покрытие работают без трансляций.

Декомиссия поллера (ME-056) открывается, когда агентная kora-нога покрыла
хосты: `ME-055 → ME-020 (эта спека) → перенос kora-ноги в агент → снятие
поллера`. До этого поллер и агент сосуществуют: двойной push в kora-scan
от одного executor_id безопасен (upsert по native_id, идемпотентен).

## 3. ME-021 — инвентарь харнесов: форма представления и состав payload

### 3.1 Вердикт: дропдауны на карточке хоста/агента в ростере ME-014, не вкладка

Выбран **дропдаун на карточке ME-014**. Обоснование:

1. Запрос владельца дословно про выпадающий список («а выпадающий список
   в интерфейсе сообщал») — форма уже выбрана заказчиком.
2. Инвентарь — контекст хоста, а не пункт навигации: владелец смотрит
   «что за хост/агент» и рядом получает «что на нём подключено». Отдельная
   вкладка превращала бы атрибут в назначение.
3. Вторая поверхность = дублирование i18n, роутинга, пустых состояний и
   SSE-связки для тех же данных. Cost без новой ценности.
4. Карточка ME-014 уже существует и уже показывает presence-чипы и
   discovery-зеркало харнесов — инвентарь ложится в тот же блок
   «Обнаружено на хосте» (07c §6, с учётом Э3).

Состав UI: счётчики по категориям видны сразу («39 специалистов · 121
скилл · 4 плагина · 24 инструкции»), имена — за раскрытием/дропдауном,
переполнение — честная строка «…и ещё N» (счётчик всегда полный, список
урезан капом). Пустой инвентарь у поллер-хоста — honest-empty плашка
эрратумы Э3 («Обнаружение установок умеет только агент (Go)…»), без
скелетонов «сканируем».

### 3.2 Состав capabilities-payload — контракт discovery v3

Зафиксирован на стороне агента (PROTOCOL §3, v3 addendum), борд принимает
и хранит как есть:

```json
{"environments": [{
  "name": "zcode", "kind": "cli", "home_path": "/home/u/.zcode",
  "capabilities": {
    "specialists": ["bathys-researcher", "gcw-tech-lead"],
    "specialists_count": 39, "gcw_specialists_count": 38,
    "skills": ["a11y-audit"], "skills_count": 121,
    "plugins": [], "instructions": ["architectural-committee.md"],
    "instructions_count": 24,
    "notes": {"agents_md": true, "gcw_managed": true}}}]}
```

- Категории: специалисты (+счётчик +доля gcw-*), скиллы, плагины,
  инструкции; `notes` — булевы метки. Правила/«и т.д.» владельца покрывает
  категория `instructions` (gcw/instructions — правила дома).
- **Имена, никогда содержимое** (секрет-дисциплина): ровно два
  ограниченных исключения на чтение — pi `agent/settings.json` (только
  имена packages[]) и zcode `AGENTS.md` (только маркер `gcw:begin`).
- Капы: списки ≤ 50 (specialists/skills) и ≤ 30 (plugins/instructions)
  имён, весь объект ≤ 8 KiB на среду; счётчики всегда полные; пустые
  списки omitempty — v2-payload байт-идентичен.
- Скан харнес-сред — обязанность агент-лейна (см. §6.4); борд не сканирует
  ничего.

### 3.3 Честная правка записи борда: поле `capabilities` у executor — НЕ то поле

В записи ME-021 принято «поле capabilities у executor в схеме уже есть».
Это **семантическое несовпадение**: `ExecutorOut.capabilities` —
владелец-объявляемый список строк маршрутизации (Amd 2 §4: никогда
не саморасширяется), а инвентарь — само-отчётный объект с четырьмя
категориями. Класть инвентарь в owner-declared поле ломает инвариант
Amd 2 §4 и тип.

**Решение:** новое additive-поле реестра, например `harness_inventory`
(окончательное имя — §7), per-executor снимок последнего discovery-отчёта
(`environments[]` как есть). Читается в OPEN-границе реестра (как
discovery-зеркало харнесов сегодня), advisory-семантика без изменений.
Схемная правда дня: `ExecutorDiscoveryBody.environments` уже принимается
как `list[dict]` и игнорируется — срез борда превращается из «принять» в
«начать хранить + отдавать».

## 4. Хранение и контракты борда (поверхность, не имплементация)

Имплементация — зона Tech Lead; спека фиксирует контрактные поверхности:

1. **Стор session-фактов** — отдельный от ADR 0019 (замороженные контракты
   вокруг Коры не трогаем): upsert по `(executor_id, native_id)` с
   `task_id`, advisory-зеркало, размер bounded (≤ 32 живых строк на
   исполнителя в духе капа агента).
2. **Чтение карточки** — замороженный `GET /api/tasks/{task_id}/sessions`,
   ui-класс (владельческая поверхность; путь хоста в факте — причина
   класса). Поля факта + возраст. SSE-словарь — опциональная
   `session.fact_listed`-метадата (грамматика slice-1: что искать, не
   агрегат).
3. **Инвентарь** — additive-поле исполнителя (§3.3), OPEN-чтение, снимок
   последнего отчёта, идентичный ре-репорт — молчаливый no-op (семантика
   discovery без изменений).

## 5. Канон честности (обязательные заглушки)

- **Нет session-фактов у задачи** — пусто с причиной, не скелетон:
  «Задачу исполнял поллер / исполнитель без агента — сессии недоступны»
  либо «Агент ещё не отчитался о сессиях» (до первого деплоя агент-ноги
  это состояние ВСЕХ строк — оно честное, не «сломанное»).
- **Транскрипт хоста, которого борд не читает** — существующая честная
  404-плашка покрытия (slice 2: remote-host → 404 до W4 loopback-ingress);
  из карточки — возврат с объяснением, не пустой экран.
- **Инвентарь поллер-хоста** — плашка Э3 («Обнаружение умеет только агент
  (Go). Этот хост подключён поллером — список появится после ME-056»).
- **Переполнение списков** — «…и ещё N»: счётчик полный, список урезан;
  урезание видно, а не молчит.
- Ничего из перечисленного не имитирует загрузку; пусто — это ответ.

## 6. Порядок внедрения

Зависимости: FE-глаза НЕ ждут агент-лейн (рендерят honest-empty), агент-лейн
НЕ ждёт FE (кладёт данные в существующую ногу discovery). BE-срез первый —
он определяет оба контракта.

### 6.1 Срез 1 — борд: хранение ингеста (BE, блокирует контрактно, не датой)

Discovery-ингест начинает хранить и отдавать: additive `sessions[]` →
стор фактов + `GET /api/tasks/{id}/sessions` (ui); `environments[]` →
`harness_inventory`-поле исполнителя (OPEN). Валидация task-linkage и
словаря (§2.2). Всё additive — старые агенты и поллеры не замечают
изменений. Честные 422 на переполнения.

### 6.2 Срез 2 — FE: карточка задачи (ME-020 MVP)

Таб «Исполнение»: блок «Специалисты и сессии» — строки (специалист,
харнес, тул-каллы, длительность, возраст) + deep-link
`/kora/sessions/{executor_id}:{native_id}` в read-only просмотрщик.
Honest-empty по §5. Отдельной страницы не строим (UXE-3 не трогаем).

### 6.3 Срез 3 — FE: ростер ME-014 (ME-021)

Карточка хоста/агента: блок «Обнаружено на хосте» получает
инвентарь-дропдауны (§3.1) из `harness_inventory`. Плашки Э3 для
поллер-хостов.

### 6.4 Агент-лейн — требования к агенту (передача в vesmaro-agent, отдельный борд)

1. **Emission `sessions[]`** — на child exit (цель ≤ 60 с, M2 устава),
   часовой sweep-догон; spawn-реестровая связь task_id→child→session-dir;
   счётчики из ограниченного чтения (размер-кап; контент никогда);
   дедуп по id; ≤ 32 строк; `specialist` из subagent_type спавна;
   `parent_native_id` при наличии цепочки.
2. **Capabilities-инвентарь** — по контракту PROTOCOL §3 v3 (уже
   специфицирован агент-стороной; сюда — только реализация скана сред).
3. **kora-нога для ME-056** — push листинга в существующий
   `POST /api/executors/{id}/kora-scan` (executor-токен, замороженный
   контракт) на том же read-only ядре чтения сиджей; cadence — наследник
   таймера поллера, решение владельца.
4. **Фаза 2 (не сейчас):** транскрипт-pull нога (fetch-on-demand через
   исходящие ноги агента) — правка never-list устава: ратификация
   владельца + свежий SEC-ревью ДО реализации.

### 6.5 Фаза 2 борда/FE (не MVP)

- Транскрипт-pull (после §6.4-4) — удалённые хосты перестают быть 404.
- Дерево субагентов/подзадач (требование №4) — из `parent_native_id` +
  разбора toolCall к агент-тулам; UI «как в zcode».
- mnd_-класс для листинга сессий задачи — только по явному решению
  владельца.
